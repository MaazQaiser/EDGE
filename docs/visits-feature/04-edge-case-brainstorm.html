The edge cases that still need answers

Options and a recommendation for each of the unresolved cases — contract compliance when visits move, where a route begins and ends, and four smaller ones that follow from letting visits float between days.

Case one · the hard one

Contract compliance when visits move

Three different failures wearing one coat

Drift. A site contracted for a change every 30 days gets each visit nudged a few days later. No single move looks wrong, but the gap creeps past 30 and stays there.

Early replacement. Pulling a visit forward by two weeks throws away two weeks of filter life. That's money on the floor, and it's the failure nobody thinks to guard against.

Period count. Move a visit from 1 Sept to 30 Aug and August now has two visits for that site, September none. If billing counts visits per month, both months are wrong.

These pull in opposite directions, which is what makes a single threshold useless. The framing that resolves it: a visit isn't due on a date, it's due within a window — too early wastes filter life, too late breaches the contract.

Options

A · Service window per visit, plus a period anchor

Recommended

Derive an earliest-useful and latest-compliant date for each visit from the site's contracted interval and its last completed visit. Show the window on every candidate; warn with a specific number of days when a move lands outside it.

Separately, tag each visit with the billing period it belongs to. Moving inside the period is silent; moving across a boundary warns that the period's count changes.

Why  Catches all three failures with one concept, and the window is genuinely useful information even when nobody is moving anything.

B · Interval guard only

Partial

Warn only when the gap since the last visit would exceed the contracted interval.

Why not  Silent on early replacement and on period counts. Cheapest to build, and a reasonable v1 if the window data isn't there yet.

C · Cascade the recurrence

Reject

Moving a visit shifts every subsequent one to preserve the interval.

Why not  A single tap to fit today's route silently rewrites months of schedule. Violates the principle that a route change is an occurrence-level act.

D · Compliance ledger, no gating

Complement

Allow everything, track per-site compliance, surface it on the site page and in a report.

Why not alone  Finds out after the fact. Good alongside A — the warning prevents, the ledger proves.

Recommendation

Ship A with D as the audit surface. Both warn, neither blocks — consistent with the day being flexible. The one prerequisite is knowing whether the contracted interval is stored per site; if it isn't, B is the fallback until it is.

Case two

Where the route begins, and where it ends

You've settled the start: current position, or an address typed in. The consequence is that the model can no longer store one startEndLocation for both ends — and the end matters more than it looks, because the drive home comes out of the eight hours.

Start

  • Current position — the default whenever the route is live. Requires a recent fix; fall back to the last known stop if the device hasn't reported.
  • Saved location — depot or home. The default when planning a future day, since "current position" is meaningless for next Tuesday.
  • Typed address — for "I'm starting from my mum's tomorrow." Needs geocoding, which the map integration already has.

End

Offer all three, default to round trip

Recommended

Return to start — the classic round trip, and what the current single-field model implies. The return leg counts against the budget.

End at last visit — an open route. Optimises differently: the solver is free to finish far from home, which often fits noticeably more work into a day.

Typed address — end somewhere specific.

Why it matters  Open versus round trip can swing the achievable visit count by one or two. Making it a visible toggle turns a hidden assumption into a lever the user can pull.

Recommendation

Show start and end as two controls directly above the capacity meter, so the effect of switching to an open route is visible as the bar shortening. Default: start = current position when live, depot when planning; end = return to start.

Case three

Site access windows versus pure speed optimisation

The optimiser can produce an impossible route

Every visit already carries a windowStart and windowEnd. If those are real site access constraints — a shop that only allows service before opening, a plant with a maintenance slot — then "fastest route" and "valid route" are different problems. A pure shortest-path solver will happily schedule the 7am-only site at 3pm.

Treat windows as soft

Interim

Optimise for speed, then flag any stop whose arrival falls outside its window.

Trade  Simple, and honest about what it can't do. The user manually reorders to fix violations, which erodes trust in the optimiser.

Treat windows as hard constraints in the solve

Recommended

Make it a routing problem with time windows rather than a plain travelling-salesman one — the standard formulation every commercial routing product uses.

Trade  Meaningfully harder, and occasionally there's no valid ordering at all, which needs its own message. But an optimiser that produces impossible routes gets switched off.

Recommendation

Hard constraints — but first confirm what those windows actually mean. If they're merely the nominal service time rather than a real access restriction, this whole case collapses and soft flagging is plenty. Worth one question to ops before any solver work.

Cases four to six

The smaller ones

Does the van have the filters?

Clubbing eight visits into a day is pointless if the van carries stock for four. The supplies forecast already computes filter quantities for a set of visits over a window, and returns { name, quantity } pairs — so the route builder can show the implied load without new backend work.

Recommendation

A collapsed "van load" panel next to the capacity meter, listing filter types and counts for the current selection. Warn on nothing initially — we don't model van stock — but seeing "14 × HEPA-12" before committing is most of the value, and it makes any future stock check a small addition.

What happens to a runsheet you emptied?

Pull all of Wednesday's visits into today and Wednesday's runsheet has no stops left.

Leave it, flag it empty, offer to delete

Recommended

Auto-deleting destroys a configured route — its hours, start location and break rule — that the user may want next week. Since a runsheet is a recurring template, deleting it removes future weeks too.

Note  This is the clearest case where template-versus-occurrence bites: the occurrence is empty, the template isn't dead.

Two visits at the same site on different days

Clubbing them means one trip serving both. Almost certainly desirable — it's exactly the saving the feature exists to find — but they stay two visit records with two service confirmations, and the route should show them as one stop with two jobs rather than two stops at the same coordinates.

Recommendation

Collapse same-site visits into a single map pin and a single row with a "2 jobs" badge; count travel once and service time twice. Actively suggest this pairing when it appears — it's free efficiency and the user may not spot it.

Recap

What each case resolves to

Case
Resolution
Contract compliance
Service window per visit (earliest useful → latest compliant) plus a billing-period tag. Warn with days, never block. Compliance ledger as the audit trail.
Route start
Current position when live, depot when planning, typed address always available.
Route end
Return to start by default; open route and custom address offered as visible toggles, because the return leg costs budget.
Access windows
Hard constraints in the solver — after confirming the existing windows really are access restrictions and not just nominal times.
Filter stock
Show the implied van load from the existing supplies forecast. Informational in v1.
Emptied runsheet
Keep the template, mark the occurrence empty, offer deletion explicitly.
Same site twice
One stop, two jobs. Suggest the pairing proactively.

Two things gate the first and third cases respectively: whether the contracted interval is stored per site, and whether a visit's time window is a real access restriction. Both are single questions to ops, and both change how much work the recommendation is.
