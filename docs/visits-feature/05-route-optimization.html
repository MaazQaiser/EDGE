Route optimization and harmonization

Two problems that get confused with each other. Optimization orders the stops inside one route. Harmonization decides which route a visit belongs to in the first place — and it is where nearly all the saved time actually is.

Three scopes sequence · day · week Never auto-applies Follows the clubbing design
Framing

Sequencing is the small half

Reordering eight stops that are already on Tuesday's route might save twenty minutes. Noticing that four of Tuesday's stops are clustered around Wednesday's patch — and swapping them — saves hours. The second is the prize, and it is the automated form of the clubbing the planner does by hand.

They need separating because they carry completely different risk. Reordering touches nothing a customer sees. Moving a visit to another day changes when someone's filters get replaced.

Scopes

Three levels, ascending risk

Each is a separate action with its own button, its own blast radius, and its own confirmation. They ship in this order.

Sequence

Level 1 · one route

Reorder the stops within a single route. Nothing changes day, nothing changes route. Purely "drive these in a better order".

Risk  Near zero. Nobody outside the van is affected. Safe to offer as a one-tap action, and safe to run on a live route.

Rebalance the day

Level 2 · routes on one day

Move visits between routes that already run on the same day, then resequence each. Changes who does a visit and when in the day, but not which date.

Risk  Moderate. Arrival times shift, so any customer expecting a morning slot is affected. No contract implications.

Harmonize the week

Level 3 · across days

Reassign visits between days to cluster them geographically, then rebalance and resequence. This is the figure above, and where the real saving lives.

Risk  High. Every moved visit changes date, which touches the service window and the billing period, and may need the customer told. Must never run unattended.

Why separate buttons rather than one clever one A single "optimize" action that sometimes reorders and sometimes silently moves a visit to Thursday is impossible to trust. The user should always know the blast radius before they press, and the wording should say it: Reorder stops, Rebalance Tuesday, Harmonize this week.
Objective

What "better" means

Optimizers need a single number to minimize, but the business has several goals that trade against each other. Rather than exposing weight sliders nobody can reason about, offer three named intents that set the weights internally.

ModeMinimizesUse when
Tightest routes Total driving time. The default, and what "fastest and most efficient" means. Normal planning. Fuel and hours are the cost being cut.
Even days Variance in day length across the week, subject to a driving-time ceiling. When one day is a 9-hour slog and another is half empty.
Catch up Total lateness — days past each visit's compliant date, weighted by how late. After a bad week, when overdue visits matter more than fuel.

All three run the same solver against the same constraints; only the cost weights differ. Showing the resulting trade explicitly — "2h 10m less driving, but Thursday grows to 8h 40m" — is more useful than letting someone tune a slider blind.

Constraints

What the solver may never do

Hard constraints make a solution invalid. Soft ones cost points but are allowed — the difference matters, because over-constraining produces "no solution found", which is the worst possible answer to give a planner.

ConstraintBehaviour
Site access windowHardArrival must fall inside it. A route that reaches a 7am-only site at 3pm is not a worse solution, it is not a solution.
Locked stopHardA stop the planner pinned to a position, a day, or a route. Never moved. This is the escape hatch that makes the whole feature usable.
Completed or in-progress stopHardFrozen. Only the remaining tail of a live route is solvable.
Latest compliant dateHardA visit may never be pushed past the date its contract requires. Pulling it earlier is allowed but costed.
Eight-hour man-daySoftHeavily penalised, not forbidden. A ten-minute overrun that saves an hour elsewhere is a trade a human should get to see.
Early replacementSoftCosted per day of filter life discarded, so the solver only pulls a visit forward when the driving saved is worth it.
Billing period boundarySoftPenalised, because moving a visit across a month changes that month's count.
Same-site clusteringFreeTwo visits at one site collapse to a single stop before solving. Travel is paid once.
Infeasibility is a UI problem, not just a solver one With hard windows it is entirely possible that no valid arrangement exists. "No solution found" is useless. The solver should instead return the best constraint-violating arrangement it found plus the specific constraint it had to break — "Harbour Way cannot be reached inside its 07:00–09:00 window from any position in this route" — so the planner can unlock something and retry.
Inputs

The travel matrix is the expensive part

Every optimizer needs the time between each pair of stops. That is where the cost and the latency are, and it is worth designing before the solver.

  • It grows quadratically. Fifty stops is 2,450 ordered pairs. A week across several routes gets there quickly, and matrix APIs bill per element.
  • But site pairs barely change. The drive from Oak Plaza to Mill Road is the same next week. Cache by site pair with a long expiry and only pay for pairs never seen before — the marginal cost of re-optimizing an existing week approaches zero.
  • The depot and "current position" are the exception. Current position is different on every request and cannot be cached, so treat it as one extra row rather than a full rebuild.
  • Straight-line distance is a fallback, not a model. The demo uses haversine over an average speed, which is fine for a preview and wrong near water or motorways — exactly the geography where routing matters most.
  • Traffic is a decision, not a detail. Time-of-day-aware durations make routes more accurate and the matrix far less cacheable. Recommend starting with free-flow durations plus a margin, and revisiting once the feature has users.
Existing constraint worth knowing Route geometry is currently fetched client-side through Google Directions with waypoint chunking, because Directions caps waypoints per request. That is fine for drawing a line on a map but is the wrong place to solve from — the solver needs a matrix, not a polyline, and it should not run in the browser.
Execution

Two engines, deliberately

Client heuristicServer solver
PurposeInstant feedback while selecting visitsThe answer that gets committed
MethodNearest neighbour over cached straight-line estimatesProper vehicle-routing solve with time windows
LatencyUnder a frame, runs on every clickSeconds for a day, longer for a week
AccuracyIndicative — good enough to show the capacity meter movingCommitted times shown to customers

The two must never disagree visibly. The client estimate drives the live meter while the planner is choosing; the moment they ask to optimize, the server answer replaces it and the meter re-renders from the real numbers. Any figure a customer might be told comes from the server.

Synchronous or not

  • Sequence — synchronous. A handful of stops solves fast enough to feel instant.
  • Rebalance a day — synchronous with a progress state. Seconds, not minutes.
  • Harmonize a week — asynchronous job. The planner starts it, keeps working, and gets a proposal when it lands. A week-scale solve is not something to hold a spinner over.
Interaction

Propose, diff, accept — never apply

The single most important rule. An optimizer that rewrites a plan the moment it is invoked will be switched off after the first time it moves something the planner had a reason for.

What the diff has to show

  • The headline trade — "1h 45m less driving. 3 visits move day. Thursday grows by 40m."
  • Per change, the reason — "Kiln Lane moved Wed → Tue: 22m closer to the rest of Tuesday's cluster, still inside its service window."
  • What got worse — stated as plainly as what got better. A proposal that only lists wins reads like a sales pitch and gets distrusted.
  • Anything needing a customer told — collected into one list, so notifying is a single reviewed action rather than a side effect.
Trust

The churn problem

Routing solutions are unstable. Add one visit and the optimal ordering can change almost everywhere, because a tiny cost improvement is still an improvement. Mathematically correct, and it makes the product feel random — the planner re-runs it, the whole week rearranges, and they stop believing any of it.

Three mechanisms, all of which cost a little optimality and buy a lot of trust:

  • Bias toward the current plan. Add a small cost to every change from the existing arrangement, so the solver only moves something when the gain clearly outweighs the disruption.
  • Suppress trivial proposals. Below a threshold — say fifteen minutes or three percent — report "already close to optimal" rather than offering a reshuffle nobody wants.
  • Deterministic tie-breaking. Identical input must give identical output. Break ties on a stable key such as site id, never on iteration order, so re-running never produces a different-but-equal answer.
The test that matters Run the optimizer twice on an unchanged week. If it proposes anything at all the second time, the feature is not ready — it means the first answer was arbitrary, and users will notice long before they can articulate why they distrust it.
Live routes

Re-optimizing a day in progress

The clubbing design already establishes that a live route is a valid target. The same rules govern re-optimization, and one more besides.

  • Solve only the tail. Completed and in-progress stops are fixed; the remaining stops are the problem to solve.
  • Anchor on the actual position, not the depot. Optimizing from the morning start point produces an order the driver has already invalidated.
  • Budget from elapsed time. Four hours already spent means four hours less to allocate, regardless of what was planned.
  • Do not resequence what the driver can see. If the next stop is already on their device and they are driving to it, reordering it out from under them is worse than a suboptimal route. Treat the next stop as locked unless they explicitly release it.

Open

Questions this raises

  1. Is there an existing routing engine to build on? There is a routing service endpoint in the codebase already. Whether it can do a constrained multi-stop solve or only returns geometry decides whether this is integration or a new component.
  2. Buy or build the solver? Mature open-source routing libraries handle time windows and capacity properly. Writing one is rarely the right call, but it does mean a service to host.
  3. What is the realistic problem size? Ten stops a day is a different engineering problem from two hundred. This is the same volume question the clubbing design left open, and it now determines the architecture rather than just the UI.
  4. Are site access windows real? Still the pivotal unknown. If they are genuine restrictions this is routing with time windows; if they are nominal service times it is far simpler.
  5. How accurate must arrival times be if customers are told them? That decides traffic-aware routing, which in turn largely decides the matrix caching strategy.
  6. Should harmonization ever run unattended — a weekly proposal waiting on Monday morning — or only on demand? Unattended is powerful and needs the trust mechanisms to be proven first.
  7. Who is accountable when an optimized route fails? If a technician runs late because the plan was tight, the audit trail needs to show the route was machine-proposed and human-accepted.
