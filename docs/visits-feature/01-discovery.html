A scheduler view for visits, and merging them into runsheets

Two related pieces of work: make every visit — assigned and unassigned — visible on the schedule, and let a scheduler pull a set of them into one runsheet. This note grounds the domain model from the code, marks where the gap is, and lists what we still have to decide.

Grounding

The vocabulary, as the code actually uses it

The product uses three overlapping words — hit, visit, runsheet — and they are not synonyms. The distinction matters because the feature sits exactly on the seam between them.

Hit
One required service occurrence at one site: a time window plus a weekday. It is the unit of demand. windowStart · windowEnd · dutyDay 0–6 · siteId
Visit
What a hit is called once it sits inside a runsheet. The runsheet's ordered list is literally visitSet, and a row in it can be a hit, a missed hit, or a dispatch. visitRowIdKey = hitId ?? missedHitId ?? dispatchId
Runsheet
An ordered route of visits for one weekday, with a start/end location, a break rule, and an assigned officer and vehicle. It is the unit of work. patrolTemplateId
Patrol ↔ Filter change
The same service. FilterGo's filter-change service is Signal's patrol service; the API says patrol either way and the UI relabels it per tenant.
Tour
The checklist performed at a hit — checkpoints and a report template. A hit without a tour cannot currently be added to a runsheet.
Today

Five places already touch hits, none of them a schedule

The capability is not missing so much as scattered. Each surface below solves one slice, with its own navigation, its own time model, and no shared picture.

Create Runsheet wizard

runSheets/details

Three steps — details, select hits, reorder. Hits arrive grouped by site for one time window. This is the existing "consolidate" path, but it always starts from a blank runsheet.

Assign Hits page

runSheets/assignHits

Lists unassigned hits for one weekday at a time and offers a runsheet dropdown per hit. The closest thing to today's answer, and the clearest thing the new view would replace.

Scheduler → Patrol tab

schedules/calendar

A week timeline whose rows are runsheets. A hit is only visible once it is already inside one — unassigned demand is invisible here.

Missed Hits drawer

schedules/components/missedHitsDrawer

A date-ranged list of hits that were missed, with a reassign-into-runsheet flow. Proves the interaction we want already works — just for one narrow status.

Site → Jobs

sites/detail/components/jobs

Assign a single hit to a runsheet from the site's own page. Fine for one site, useless for planning a week across a franchise.

The useful surprise The write primitive for consolidation already exists and is already bulk-shaped. addHitToRunsheet takes an array of runsheets, each carrying an array of hits and its recomputed pathData. Merging N visits into one runsheet is one call, not N.
The gap

The schedule is drawn at the wrong altitude

The Patrol tab answers "what are my routes doing this week". The question this feature asks is "what work exists this week, and what has nobody picked up" — which the current grid structurally cannot show, because unassigned demand has no runsheet to be a row of.

Part A

What the visits view groups by

The scheduler already supports swapping the row axis per tab — Dedicated groups by location, Patrol by runsheet, Officer by officer. A visits view is a fourth configuration, not a new engine. The real decision is what the rows are.

A · Unassigned band pinned above site rows

Recommended start

One sticky band at the top holds every unassigned visit for the week; below it, one row per site carrying that site's assigned visits. Answers "what is unclaimed" in the first screenful, which is the stated goal.

Cost  Site rows grow long for large franchises; needs the existing virtualization flag and a site filter to stay usable.

B · Rows are runsheets, expandable to their visits

Smallest diff

Keep the Patrol tab and let each runsheet row expand into its ordered visits, with the unassigned band added above. Reuses the Overview tab's existing expand/collapse machinery.

Cost  Still runsheet-first. A scheduler asking "when is Oak Plaza serviced" has to know which runsheet to open.

C · Rows are officers

Wrong altitude

Load-balancing view — who is carrying how much. Genuinely useful, but it answers a staffing question, and unassigned visits have no officer to sit under.

Cost  Doesn't serve the primary goal; better as a later toggle than the first build.

A and B are not exclusive — the row axis could be a control on one tab. Worth deciding whether that flexibility is v1 or v2.

Part B

Merging selected visits into a runsheet

Once visits are marks on a grid, multi-select is natural and the write already exists. Two destinations, and they behave differently enough to be worth separating.

Into a new runsheet

Selection becomes the runsheet's visitSet, then the user still has to supply what only a human knows: name, start/end time, start/end location, break rule, officer, vehicle. That is exactly the existing wizard's step 1 and step 3 — so this should hand off to the wizard pre-seeded, not reimplement it.

Into an existing runsheet

The lighter and probably more common case: pick a target runsheet, append the visits, recompute the route. This is what addHitToRunsheet already does, and what the missed-hits drawer already does for one hit at a time.

Open  Does the route re-optimize automatically, or does the user land in the reorder step to confirm?

Edge cases

Where this gets hard

Grouped roughly by how likely they are to change the design rather than just the code. The ones marked blocking need an answer before UI work starts.

Weekday, not date

Blocking

Hits and runsheets are keyed to dutyDay 0–6, and the assign page works one weekday at a time. A week grid implies calendar dates. Are we scheduling a recurring pattern or specific dates?

daysOfWeekWithVal · /unassigned/hits/{day}

Hit with no tour

Blocking

Today a hit without a tour template is refused and the user is pushed into a tour-assignment drawer. In a bulk merge of 20 visits, what happens if three lack tours — block all, skip them, or merge and flag?

NoTourTemplateModal · UnassignedHits.handleAction

Window vs runsheet hours

Blocking

A visit carries its own windowStart/windowEnd; the runsheet has its own start and end. Merging a visit whose window falls outside the runsheet's hours either has to widen the runsheet, warn, or refuse.

getHitsForRunSheet filters by window

Drive time and feasibility

Design

Nothing stops a user selecting visits 60 miles apart. The route service returns pathData and an estimated time — do we surface projected overrun before committing the merge?

getRunsheetsPath · estimatedTime

Moving an assigned visit

Design

Merging a visit that already belongs to runsheet A into runsheet B is a remove-then-add across two routes. Both need reordering, and A may become empty.

removedHits · isVisitsUpdated

Mixed row types

Design

A visitSet row can be a hit, a missed hit, or a dispatch. Does the new view show all three, and can all three be merged the same way?

visitRowIdKey

In-flight runsheets

Design

A runsheet that has started, is mid-break, or is completed. Adding to a live route is very different from planning next week's.

ShiftStatus · shiftStarted

Cancelled and missed

Rules

Hit-specific statuses missed, cancelled, incomplete already exist. Missed has its own reassign path today — does it fold into this one or stay separate?

calendarShiftStatusEnum

Break rules

Rules

Runsheets carry a break rule and a payable flag. Growing a route past a threshold may change which break rule applies.

breakRule · isBreakPayable

Split runsheets

Rules

A runsheet can be split across officers, and Splitted is a first-class status. Merging into one half of a split needs defined behaviour.

splitRunSheet

DST and timezone

Known pain

The codebase already carries DST-specific helpers, which says this has bitten before. A week grid spanning a DST boundary will expose it again.

getCurrentTimeWithDisabledDlsInIso

Scale

Perf

Visits are an order of magnitude more numerous than runsheets. Row virtualization exists but is behind an env flag, and the unassigned endpoint is one-day-at-a-time.

To resolve

Open questions

Scope and shape

  1. Who is this for? A dispatcher planning next week, or a supervisor reacting today? The first wants density and bulk actions; the second wants status and exceptions.
  2. Is this FilterGo-only, or does Signal get it too? The code path is shared — patrol either way — so a Signal-visible feature costs little extra but changes the labelling work.
  3. New tab, or a mode on the existing Patrol tab? Affects whether the header tab list becomes tenant-conditional.
  4. Recurring pattern or dated occurrences? The single biggest fork. Everything downstream — grid, merge, conflict rules — depends on it.

The merge interaction

  1. How are visits selected? Checkboxes, marquee drag on the grid, or a side basket that accumulates across days.
  2. Can a selection span multiple days? If a runsheet is one weekday, a cross-day selection has to either split into several runsheets or be refused.
  3. Is drag-and-drop of a visit onto a runsheet row in scope, or is merge always an explicit action?
  4. After merging, where does the user land? Back on the grid, or in the reorder step to confirm the route.
  5. Is unmerge / eject in scope for v1?

Rules we need from ops

  1. What makes a merge invalid versus merely warned? Distance, duration, window conflict, missing tour, officer hours.
  2. Is there a cap on visits per runsheet, or on route duration?
  3. Who is allowed to do this? There is an existing ACL pattern; we need the permission for bulk assignment.
  4. Does the officer get notified when visits are added to a route they already own?
  5. What must be audited? hitAdded / hitRemoved log actions exist — is a bulk merge one log entry or many?
Next

Suggested order

Settle Q4 first — recurring versus dated decides the data contract and most of the edge cases. Then agree the row axis from Part A, since that is what the backend needs to know to shape the grid response. The merge interaction can be designed in parallel once the blocking three edge cases have rules attached.

Worth confirming with someone who has run the operation: whether schedulers actually think in "unclaimed work this week", or whether they think per-site and the unassigned band is the wrong hero.
